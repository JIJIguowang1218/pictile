# 关于"可复现性"的再讨论

> 状态：对 [`05-技术调研-P1P2P3.md`](05-技术调研-P1P2P3.md) §8.1 的**修正**。
> 起因：用户质疑"在 AI 创意生成领域追求完全可复现是否必要"。
> 结论先行：**质疑基本成立。我上一轮把四种完全不同的东西混成了"可复现"一个词，并用错了理由。**

---

## 1. 我把四件事混成了一件事

上一轮说"LLM 自由选工具会导致不可复现，所以只能从菜单里选"。这句话把下面四件事压成了一个词：

| # | 概念 | 定义 | 在创意产品里是否必要 |
| --- | --- | --- | --- |
| ① | **渲染确定性** | 同样的图 + 同样的参数 + 同样的色板版本 → 同样的图纸 | **必要**，但这是编译器的性质，不是创意的性质 |
| ② | **成品冻结** | 用户认可的成品，之后不会自己变 | **必要**，且和"复现"无关 |
| ③ | **变更可追溯** | 能看见改了什么、能回退 | **必要**，比 ① 更有价值 |
| ④ | **建议可重跑** | 同样输入得到同样的建议/同样的一句话 | **不必要**，甚至有害 |

我上一轮讲的是 ④，但真正需要的是 ①②③。**这就是表述错误。**

一个现实类比：没人要求调色师"第二次调色必须和第一次一模一样"，但所有人都会要求"定稿之后别再动我的片"。

---

## 2. 哪些必须确定，哪些不该确定

### 2.1 必须确定的

| 对象 | 为什么 |
| --- | --- |
| 渲染器（采样 → 量化 → 清理 → 排版） | 它是编译器，不是创作者。生成图纸的过程里没有任何需要"灵感"的地方 |
| 数值工具（ΔE、色数、计数、成本） | 同样的输入给出不同的数，是 bug，不是多样性 |
| 已冻结的版本 | 用户按这张图买了豆子、打了印、拼到一半，图不能变 |
| 批量/复用场景 | 摊主给客户做 50 个一样的，必须能稳定重出 |

### 2.2 不该确定的

| 对象 | 为什么 |
| --- | --- |
| 建议的措辞 | 同一张图两次说成不同的话，用户不会觉得是 bug |
| 候选的排序 | 略有波动反而让"再来一版"有意义 |
| 创意方向（风格化、构图取舍） | 变化本身就是价值；用户要的是"再给我一个版本" |
| 检查项的先后 | 只要最终结论一致，顺序无关 |

### 2.3 一条可以直接写进代码的原则

> **生成可以随机，应用必须确定。**

- **生成**：建议、措辞、候选、风格，全部允许随机。
- **应用**：一旦用户点了"采用"，这次变更就以一个确定参数集写进版本栈，执行结果必须完全确定。

不确定性被关在两个笼子里：**它只能出现在"提议"环节，永远不能出现在"执行"环节。**

---

## 3. 真正的目标不是"复现"，是"收敛"

用户要的不是"再来一次结果一样"，是**每次交互后，离他想要的东西更近**。这在产品上叫收敛性（convergent interaction），需要五个条件：

1. **预期可见**：动手之前就知道会发生什么（由数值工具预测，不是模型猜）。
2. **单步可逆**：每次变更进版本栈，不是覆盖。撤销的是"这一步"，不是"全部"。
3. **变化显式**：给出 diff——改了几格、几色、多几颗豆、多几分钟、多几块钱。
4. **系统主动引导**：不是等用户摸索，而是主动说"现在最影响成品的是这 3 处，建议先修第 1 处"。
5. **停止条件明确**：指标达标或用户确认，就停，不继续打扰。

这五条里没有一条要求"可复现"。它们要求的是 **可控、可逆、可见**。

### 3.1 为什么这比"可复现"更符合创意工作的本质

创意工作的实际形态是"说不清 → 看到一个具体的东西 → 反应 → 修正"，而不是"描述清楚 → 一次生成正确"。所以产品的核心能力是**接住那个模糊的反应并把它变成下一步**，不是保证第一次就对——更不是保证第二次和第一次一样。

---

## 4. "LLM 只能从菜单里选"的理由，需要换掉

结论不变，但理由要换成更强的四条：

| 旧理由（不成立） | 新理由（成立） |
| --- | --- |
| 保证可复现 | **可预测**：用户按的每个按钮，结果必须符合预期 |
| — | **可验证**：工具能实测"改了之后有没有变好"，自由编排无法验证 |
| — | **成本与延迟可控**：自由编排的调用次数不可控 |
| — | **安全边界**：避免模型产生无法执行、无法解释、无法撤销的动作 |

注意最后一条：这不是为了"可复现"，而是为了**不产生用户无法理解的变更**。这和收敛性是同一个目标。

---

## 5. 那还需要记录"配方"吗？需要，但目的不同

记录 `配方`（参数集 + 色板版本 + 工具输出快照）不是为了"重跑出一样的结果"，而是为了：

- 撤销与版本对比
- 分享（用户之间传"配方"比传提示词可靠）
- 批量生产（摊主复用同一份配方）
- 调试与回归测试（"上次这个图能过，现在过了吗"）

**关键区别**：存的是**执行用的参数**，不是**模型的原始回复**。参数是确定的、可审计的、可跨设备复用的；模型回复是建议，建议本身不需要存档，只需要把"被采纳的建议"落成参数。

这也解释了 Hon-Wong/pindou 为什么做"参数 JSON 导入导出"——那正是配方，而不是"复现随机生成"。

## 6. 仍然保留的确定性要求（缩小后的清单）

| 要求 | 范围 | 备注 |
| --- | --- | --- |
| 渲染函数纯函数化 | 内核 | 不读环境、不读时间、不随机 |
| 数值工具可复算 | 诊断层 | 同输入同输出 |
| 版本不可变 | 产品层 | 采用即冻结 |
| 回归基线 | 工程层 | 用固定图集跑指标，不比对像素 |
| 跨设备一致 | 批量场景 | 靠色板版本 + 配方，不靠模型 |

注意"回归基线"这一条：**不是比对两张图是否逐像素相同，而是比对指标是否退化**。这是更实用的工程做法。

---

## 7. 结论

1. **你对"完全可复现"的质疑是对的**，在创意生成里它是伪需求，也确实是少数人的做法。
2. **但"不随机"仍然必要**，只不过范围很窄：渲染器、数值工具、已冻结的成品。
3. 真正的产品目标是 **收敛**，不是 **复现**。收敛靠的是：预期可见、单步可逆、变化显式、主动引导、停止明确。
4. 我上一轮拿"可复现"当理由去限制 LLM 的自由度，是**理由错了、结论对了**。正确的理由是：可预测、可验证、成本可控、不产生无法撤销的动作。
5. 允许随机的地方要说清楚：**提案层随便随机，执行层一律确定。**
