# 头脑风暴：AI 介入边界、色彩策略与技术栈

> 状态：**发散稿**。不是定稿，用来给 [`02-技术方案与关键决策.md`](02-技术方案与关键决策.md) 的 `D-` 清单提供选项和论据。
> 本文出现的具体品牌色号数量、规格比例为**待核实**项，落地前必须用实物色卡校准。

---

## 0. 一句话结论

**"图片 → 色块图"这一步不该由模型做，应该由算法做；AI 的价值在它前面的"看"和后面的"评"。**

把 AI 从画布中央挪到两侧，是这个产品最重要的架构决策。

---

## 1. 核心问题：色块图转换需要 AI 吗

### 1.1 先把"AI 介入"拆成四件不同的事

讨论"要不要 AI"经常吵不出结果，因为四个人在说四件事：

| 代号 | 形态 | 例子 | 是否该用 |
| --- | --- | --- | --- |
| **A. 推理介入** | 神经网络直接算出目标像素 | 生成模型做降采样/调色 | ❌ 不该 |
| **B. 理解介入** | 模型输出"哪里重要"的软信息 | 主体分割、人脸关键点、OCR、显著性 | ✅ 高价值 |
| **C. 评判介入** | 模型给结果打分、指问题 | VLM 看图纸说"脸糊了" | ✅ 高价值 |
| **D. 对话介入** | 模型把人的模糊语言翻成参数 | "再卡通一点"→ 参数补丁 | ✅ 高价值 |

绝大多数"AI 产品"的失败，是把 A 当成 B/C/D 来做——用生成模型干活，然后不可控。

### 1.2 四道判据：什么时候该上模型

按顺序问，任何一道答"否"就不该上：

1. **能写成目标函数吗？** 能 → 用算法。
   网格采样、调色板映射、孤立豆清理、多板切分，全都有明确目标函数（最小化感知误差、满足色数/板数约束）。这是约束优化，不是感知。
2. **需要"什么重要"的先验吗？** 需要 → 用感知模型。
   "眼睛比背景重要"这件事，从像素统计里推不出来。显著性/人脸/文字只能靠模型。
3. **验收标准是主观的吗？** 是 → 用模型当裁判。
   "像不像""好不好拼"，没有闭式解。VLM 适合做排序和挑刺。
4. **用户说的是人话吗？** 是 → 用 LLM 做控制层。
   "想更清爽一点"没人能翻译成参数，LLM 可以。

### 1.3 为什么 A 一定不该用（对着拼豆场景说）

| 生成模型的固有缺陷 | 在拼豆场景里的后果 |
| --- | --- |
| 不可复现 | 同一张图两次出不同图纸，用户按昨天的图买了豆子，今天重开对不上 |
| 不可局部修正 | 用户只想改 3 个格子，模型会重绘整张 |
| 不可解释 | "为什么这块变红了"没法回答，而用户要为此拼 3 小时 |
| 幻觉细节 | 生成出不存在的花纹，拼出来才发现不对 |
| 成本 ×100 | 一次推理换 300 行 numpy 就能做的事 |

拼豆图纸是**要被照着执行几小时的施工图**，用户对稳定性的要求远高于对惊艳度的要求。这和"生成一张好看的图"是完全不同的产品类别。

### 1.4 AI 真正的价值在哪：输入侧和验收侧

一个反直觉的估算：

```
转换侧：  算法 300 行 → 85 分；  AI 花 100 倍成本 → 87 分
输入侧：  算法 60 分（原图直接喂进去）→ AI 智能裁剪/构图/风格化 → 85 分
```

**从 60 分到 85 分的杠杆在输入侧。** 用户给一张背景 70% 是杂物、人脸只占 5%、光线发蓝的照片，任何降采样算法都救不回来；而"自动裁到主体 + 校正白平衡 + 提示重拍"能救回来，且成本极低。

### 1.5 分层介入模型（建议的落地架构）

```
T0  确定性内核        50–300ms   ¥0        覆盖 70–80% 的图
T1  感知增强          1–3s       ¥0.001    按需触发 / 用户升级
T2  VLM 裁判 + 顾问   3–8s       ¥0.01–0.05  质量指标不达标时才调
T3  生成式（可选）    10–40s     ¥0.05–0.5   文本出图 / 风格化，显式选择
```

关键规则：**T2 必须由 T0 的确定性质量指标触发，不允许每张图都调。**
不能把"要不要调 AI"交给感觉，要交给阈值。

候选代理指标（全部可确定性地算出来，无需模型）：

- 结构保真度：源图与输出图在边缘图上的相似度（SSIM on edges）
- 孤立豆比例：`1–2 格连通块 / 总格数`，>3% 视为噪点超标
- 调色板浪费：被使用次数 < k 的颜色数（选了却几乎不用 = 白买了豆）
- 色差分布：逐格 ΔE00 的 P95（不是均值，均值会掩盖局部灾难）
- 跨区断裂：主体掩码内的连通性
- **缩略图测试**：把成品缩到 3cm 物理尺寸看还认不认得出（见 §5.7）

任何一个指标越线 → 升级到 T2，让模型诊断 + 生成修复建议。

### 1.6 一条硬规则：LLM 永远不碰数字

让模型判色是灾难——VLM 对精细色差的分辨能力远不如 ΔE00，而且会说得很自信。

正确的分工：

| 维度 | 谁来做 |
| --- | --- |
| 色差、色数、豆子数、板数、成本、耗时 | **确定性计算** |
| 语义（脸糊了、眼睛丢了、背景太乱、构图偏了） | VLM |
| 把"再亮一点"翻成参数 | LLM（输出结构化参数，不输出像素） |
| 解释"为什么偏灰" | LLM 读确定性报告后组织语言 |

推荐的做法是**工具调用式顾问**：LLM 只能从白名单里选动作和参数，动作由确定性模拟器执行并实测改进量；改进量 < 阈值就驳回并回灌给 LLM 重试。模型负责"选"，不负责"算"。

裁判输出建议固定 schema：

```json
{
  "verdict": "fail",
  "issues": [
    {
      "type": "feature_lost",
      "region": [12, 4, 20, 10],
      "severity": 0.8,
      "desc": "眼部被压成单色，五官不可辨",
      "action": { "tool": "raise_detail", "params": { "region": [12, 4, 20, 10], "factor": 2 } }
    }
  ],
  "suggested_variant": "detail_first"
}
```

`action` 必须是白名单工具；执行器实测通过才采纳。这样幻觉无法变成错误输出。

### 1.7 一个值得警惕的陷阱

"AI 生成底图"路线（文本 → 像素风图 → 拼豆）看起来最像 AI 产品，实际上是最容易翻车的一条：

- 生成图本身可能不适合拼豆（渐变、半透明、细碎纹理）
- 用户描述不清时，模型给的图"好看但不想要"
- 一次 30 秒 + 几毛钱，用户会反复重试，成本失控

如果要做，提示词里必须直接约束"扁平色块、无渐变、粗轮廓、≤N 色"，并且**生成结果必须先过 T0 的可拼性检查**再展示。

## 2. 色彩：有限色板下的转换策略

这是整个产品最硬、也最容易被低估的部分。

### 2.1 "取最近色"是错的，错在三个地方

1. **色差度量错**：RGB 欧氏距离与人眼感知严重不符。必须 CIELAB + CIEDE2000；深色区和低饱和区建议用 CAM16-UCS 做交叉校验（CIEDE2000 在暗部偏差较大）。
2. **目标错**：逐格独立取最近色 = 逐格独立最小化，全局是次优的，且会制造色块噪点。应该做**全局的调色板子集选择 + 分配联合优化**。
3. **参照错**：屏幕上算的是 sRGB，用户看到的是**塑料豆在室内光下的实际颜色**，熨烫后还会有光泽和轻微色变。参照系就错了，算得再准也白搭。

第 3 点意味着：**色表数据必须来自实物测量，而不是官方 RGB 值。** 官方色值通常欠饱和、批次有漂移。这是产品的地基，也是最容易被忽略的一环。

### 2.2 六种转换策略（应该在 UI 里可选）

| 策略 | 做法 | 适合 | 代价 |
| --- | --- | --- | --- |
| **S1 全局最优子集** | 把"选颜色"建成设施选址问题：从色板里选 N 色，最小化全图加权感知误差（k-medoids + 交换精化） | 默认 | N 大时局部最优 |
| **S2 按语义分区配额** | 先分区（主体/背景/皮肤/文字），给每区分配色数预算，区内独立选色 | 背景吃光色数预算时 | 需要分割 |
| **S3 保相/保明** | 被迫近似时，按区域选择牺牲哪一维：肤色保色相牺牲彩度，金属/白色保明度牺牲色相 | 人像、金属质感 | 需要区域分类 |
| **S4 描边换色数** | 自动沿轮廓加一圈深色豆，把区域切分开；分区后可减 20–30% 的色数 | 几乎所有人像/角色 | 描边过重会显脏 |
| **S5 反补偿预处理** | 在源图上先做色域预压缩（降饱和、提亮），让量化后的落点更接近意图 | 色板色域缺口大时 | 用户觉得"原图被改了" |
| **S6 有序抖动** | 只在指定区域用 1:4 / 1:2 的棋盘格造中间色 | 小面积渐变、皮肤过渡 | 制造噪点，慎用 |

S1 的失效模式必须提前防：**纯目标函数最优会选出 8 个几乎一样的灰。** 加多样性/和谐约束（明度阶梯、色相间隔、彩度层次），选出的 N 色要像一套**色阶**，而不是 N 个近似色。这一条几乎没人做，但直接决定成品好不好看。

S5 值得单独说："反补偿"是个很妙的思路——既然输出端有确定的色域缺口，就在输入端预先把图往缺口方向推。它是确定性的、可模拟的、可解释的，比让模型"生成一个更合适的图"可控一百倍。

### 2.3 色板缺口怎么向用户解释

用户不懂 ΔE，但能听懂这句话：

> "你选的这套豆子里最接近这个蓝紫的是 S22，它会比原图暗一档、偏灰。换成 S18 更亮但会偏紫。这块区域建议直接用深色描边吃掉，反而更精神。"

这段话的每个数字都来自确定性计算，LLM 只负责组织语言。这个"解释器"能力比"生成器"能力值钱得多。

### 2.4 有限色板下的调节：不要给滑杆，给结果

非专业用户理解不了"色相/明度/彩度/抖动强度"。正确做法是把参数空间投影成**结果语言**：

| 用户语言 | 内部参数 |
| --- | --- |
| 更像原图 | 提高色数、降低形态学清理强度、关闭描边 |
| 更好拼 / 少买点豆 | 降色数、加大色块、启用 S4 描边 |
| 更亮 / 更暖 / 更干净 | 色板映射的误差加权调整 + 白平衡预补偿 |
| 更卡通 / 更有像素味 | 提高饱和、减色、强制 1px 描边、块状化 |
| 保留脸 / 去掉背景 | 区域级权重（不是全局参数） |

配合三种交互，从低到高：

1. **A/B 对比**：并排给 2–3 个候选变体，用一句话标注差异，让用户选。用户不做参数决策，只做偏好决策。
2. **点选局部**：点脸的某块 → "这里想更白" → 只在该区域加约束重算，显示前后对比。局部修改比全局修改好理解得多。
3. **误差热力图**：直接给用户看"这 3 处是主要失真"。把不可见的算法误差变成可见的图，用户会自己提出合理诉求。这个功能成本极低、信任收益极高。

底层的工程支撑是 **Pareto 前沿预计算**：沿"细节 ↔ 成本"一次性算 N 个候选，拖动滑杆时只是切换到最近的候选，所以感觉是即时的、无限的。

### 2.5 多模态在色彩环节的边界

| 该做 | 不该做 |
| --- | --- |
| 看渲染后的成品图，指出"左脸暗部和背景混在一起" | 判断"色差 4.2" |
| 比较两个变体，说"B 更清爽但眼睛不如 A" | 决定具体选哪个色号 |
| 读确定性报告，翻译成中文建议 | 自己估算豆子数量 |
| 根据原图问 1–2 个澄清问题（"你更想保留衣服花纹还是脸部细节？"） | 一次问 5 个问题 |

一句话：**模型的输入应该是"已经算好的差异"，不是"原始像素"。**

## 3. 细节调节：一个滑杆，三个旋钮

用户感知的"细节多/少"实际上是三个耦合参数：

```
细节 = f( 有效分辨率(板数) , 色数 , 形态学清理强度 )
```

分开摆三个滑杆，用户会互相打架。建议**对外只有一个"细节"轴，内部映射到前沿上的一个点**，并在旁边实时显示代价：

> 细节 62% · 需 4 块板 · 9 色 · 约 1180 颗 · 拼装约 2.5 小时 · 约 ¥38

**把滑杆的坐标轴从"抽象参数"换成"时间+钱"，是这类工具最重要的产品设计之一。** 真正的约束从来不是分辨率，是用户的耐心和预算。反过来说，更好的入口是让用户直接说"我有 2 小时、50 块钱"，由系统反解出参数。

配套三个局部能力：

- **保护刷 / 删除刷**：刷过脸 = 优先保留；刷过背景 = 优先丢弃。比全局滑杆直观，非专业用户也能用。
- **增色提示定位**：加色时不均匀降阈值，把新颜色优先分配给误差最高的格子（按误差热力图分配），而不是平均撒。
- **"能不能拼"预检**：中文在 29×29 上基本拼不出来（单字至少要 12×12），要在生成前就明确告知并给替代方案（放大、换图标、改英文），而不是生成完了让用户自己发现。**提前否定不可能的需求并给替代，是专业感的主要来源。**

## 4. 国内色号体系（待核实，落地前必须校准）

### 4.1 现状判断

国内**没有统一国标**，是"事实标准"的混战。玩家实际面对的是三套并行体系：

| 体系 | 归属 | 编码形态 | 量级（待核实） |
| --- | --- | --- | --- |
| **Artkal 系**（阿特卡尔） | 中国/香港厂商，国内市占最高 | 字母系列 + 两位数字（如 `S01` / `C05` / `Rxx`）；S≈5mm 软豆、C≈2.6mm 迷你豆 | 每系列 100–200+ 色 |
| **Hama 系** | 丹麦 | 纯数字编号，midi/mini 两档 | 约 60 色（midi） |
| **Perler 系** | 美国 | 英文色名（White / Cheddar…） | 约 90–100 色 |
| **国产杂牌** | 电商白牌 | 编号混乱、跨批次色漂严重、无公开色值 | 几十色 |

关键结论有三条：

1. **Artkal 是国内事实标准**，2.6mm 迷你豆是主流规格（小挂件场景）。做色板首先做 Artkal 的 C 系列。
2. **跨品牌等价表是刚需，也是护城河。** 用户手里是 Hama，图纸是 Artkal 出的——自动换算并标注 ΔE，这个功能几乎所有工具都没有。
3. **官方 RGB 值不可信。** 必须自己用分光测色仪（几百到几千元）逐色实测，产出 `色号 → 实测 LAB(D65) → 熨烫后 LAB` 的数据表。这份数据是长期资产，比算法难抄。

### 4.2 数据层建议

```
palette/
  artkal-c-2.6mm.csv     # code, name, lab_d65, lab_ironed, measured_at, instrument, batch
  artkal-s-5mm.csv
  hama-midi.csv
  perler.csv
  equivalence.csv        # brand_a, code_a, brand_b, code_b, delta_e
```

- 每条色值带 **provenance**（测于何设备、何时、哪批）。
- 版本化，色表升级要能回答"上个月的图纸按新色表差多少"。
- 留一个 `sRGB_approx` 字段给屏幕预览用，但**算法只用实测 LAB**。

## 5. 技术栈估计

### 5.1 推荐路径（分三阶段，不要一步到位）

**阶段 0 · 算法验证（1–2 周）**
- Python 3.11 + numpy / opencv / scikit-image / `colour-science` + Jupyter
- CLI：`pictile in.jpg --boards 1 --colors 12 --palette artkal-c -o out.pdf`
- 目标：跑通 20 张真实图，建立主观评分基线

**阶段 1 · 可用产品**

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | Next.js (App Router) + TypeScript + Tailwind + shadcn/ui | 生态最顺，迭代快 |
| 画布 | Konva.js（交互编辑）/ PixiJS（WebGL 大网格 + 真实感预览） | 100×100 以上用 WebGL，否则 Canvas 够 |
| 实时重算 | Web Worker + 热路径移植（或 Rust→WASM） | 拖滑杆要 30fps，不能等 API |
| 后端 | FastAPI（CPU 容器） | 图像/色彩生态只在 Python 成熟 |
| 算法内核 | `pictile-core`，纯函数、无副作用、可单测 | 同时供 CLI / API / 未来 WASM 使用 |
| 数据 | SQLite / Postgres + 版本化色表 CSV | 色表是资产，要能 diff |
| AI | 云端 VLM（结构化输出）+ 可选本地小模型（rembg / MediaPipe / PaddleOCR） | 中文 OCR 用 PaddleOCR |
| 导出 | Python reportlab/WeasyPrint 出 PDF；前端 canvas 出 PNG | 必需 **1:1 打印标尺** |
| 部署 | Vercel + 单容器 | 初期无需 GPU |

**阶段 2 · 性能优化**
- 把内核迁到 Rust（`pictile-core` crate）：`wasm-bindgen` 给前端、`PyO3`/maturin 给 Python。**单一真相源**，避免 JS/Python 双实现漂移。
- 只有在"前端实时性"真的成为体验瓶颈时才做，不要一上来就上 Rust。

### 5.2 明确不选

| 选项 | 不选的理由 |
| --- | --- |
| Electron / Tauri 首版 | 分发、更新、签名成本高，收益不明显 |
| 纯前端首版 | 感知模型基本不可用，AI 能力被砍掉一半 |
| GPU 推理 | 非生成式路线全是 CPU 活，没必要 |
| 自训模型 | 感知类用现成的（SAM / BiRefNet / InsightFace / PaddleOCR），别造轮子 |

### 5.3 一条架构原则：内核本地，AI 异步

- 所有确定性计算在浏览器本地跑 → 300ms 出首图、离线可用、隐私好、拖滑杆无延迟。
- AI 结果以"追加变体"的形式异步到达，用户可接受/忽略。
- 这个原则同时解决了三个问题：**延迟、成本、隐私（人像照片不必上传）**。

### 5.4 一个真实的取舍：Python 内核 vs Rust 内核

| | Python 先 | Rust 先 |
| --- | --- | --- |
| 算法迭代速度 | 快（色彩库现成） | 慢 |
| 前端实时性 | 需二次移植 | 天生满足 |
| 双实现漂移风险 | 高 | 低 |
| 结论 | ✅ 阶段 0/1 | 阶段 2 迁移 |

**先 Python 验证，别过早优化。** 但写内核时就要约束自己：纯函数、只依赖 ndarray、不掺 IO——迁移成本才可控。

### 5.5 隐私与人像

用户输入大概率是人像（爱豆、宠物、孩子）。上传即涉及敏感数据。建议：

- 默认本地处理，上传为显式选择（"需要 AI 增强"时才传）
- 服务端存储 24h TTL，不做训练
- 明示"我们不会用你的照片训练"

### 5.6 打印保真

图纸必须 1:1 打印，否则全盘皆错。做法：每页角落印一个 **10mm 标尺条**，用户拿尺子量一下就知道打印机有没有缩放。极低成本，极高专业感。

### 5.7 缩略图测试（低成本高收益）

屏幕上看清楚 ≠ 拼出来看得清。把成品缩到**实际观看尺寸**（如 3cm）渲染一版，做"眯眼测试"。看不出来就说明细节白拼了。确定性、零成本、非常有说服力，应该进质量门禁。

## 6. 发散：可能没想到的十六个点

### 产品形态类

1. **按"时间 + 预算"反解，而不是按参数正推。** 输入"我今晚只有 2 小时、想花 40 块"，系统选板数/色数。这是把用户心智模型直接做成入口。
2. **同源三档打包**：一次上传，同时给 29×29 挂件 / 2 板 / 4 板海报三个版本 + 各自成本。用户看到价格差再决定，比先选参数再试错体验好得多。
3. **输入类型路由器**：先判断这张图是照片 / 插画 / 已有像素画 / logo / 文字，走完全不同的流水线。logo 和文字应该**矢量化后栅格化**（potrace → 网格吸附），比降采样好一个量级。这个分类器是个几十行的轻量模型，投入产出比极高。
4. **按库存出图**：用户拍一张自己的豆盒照片 → 视觉识别现有颜色 → 只用库存颜色出图 + 告知"缺 3 色，最少再买 2 包"。这是国内用户最真实的场景（豆盒里剩一堆零散色）。
5. **拼装引导**：图纸只是静态的。可以做"按色分批拼"（一次只拼一种颜色，拼完打勾）、甚至摄像头 AR 高亮下一颗豆的位置。前者便宜且实用，后者是传播素材。
6. **成品回流校准**：用户拼完拍照回传 → 比对预期 → 学习"这个色号在用户手里实际长什么样"。这形成数据飞轮，也是唯一能持续改进色表的机制。

### 视觉/算法类

7. **观看距离驱动的简化**：按成品预计观看距离（挂件 20cm / 海报 1.5m）算角分辨率，反推需要多少细节。没人这么做，但它在物理上是唯一正确的判据。
8. **符号化图纸**：十字绣靠符号而不是靠颜色区分色块，因为彩色打印不可靠、也照顾色盲。拼豆应该直接学这个——色块 + 符号 + 高对比网格，顺带解决色盲可用性。
9. **色盲模拟与重映射**：模拟红绿色盲看成品，若两个关键区域塌陷，自动调整色阶或改用符号区分。社会价值 + 差异化。
10. **结构接缝优化**：多板拼接不要直线切，做**错缝**（像砌砖），并把接缝放在低信息区域（背景）。这是纯确定性的几何优化，但几乎没人做。
11. **像素风"技法库"**：1px 深色描边、稀疏高光点、棋盘格假中间色、透明豆做闪光、夜光豆做点缀。把老玩家的手工经验做成可勾选的技术预设。

### 商业/数据类

12. **跨品牌色号等价表**（见 §4）。这是唯一天然可防御的数据资产。
13. **拼豆可读性指数**：把 §1.5 的指标做成对外可见的分数（主体可辨 / 噪点数 / 色偏 / 跨板风险）。公开标准 = 话语权。
14. **小店批量模式**：摊主要做 50 个一样的，需求完全不同——色数极少、区域极大、对称性好、要能流水线分工。这是另一个产品，但客单价高得多。

### 风险/边界类

15. **IP 与肖像**：爱豆照片、游戏角色是主要需求，也是主要风险。需要明确的用户协议与"仅供个人使用"提示，不做成品代售。
16. **"看起来能拼"的骗局**：任何工具都能出图，但 60% 的图拼出来是废的。**把"这张图适不适合拼豆"做成一个前置判断**（而不是事后道歉），可能是这个产品真正的差异化——它敢于说"这张不行，但我可以这样帮你"。

## 7. 建议的最小验证路径

按"先证明差异，再证明工程"的顺序：

1. **纯算法 CLI**，Artkal C 系列色表（先手工录 40 色足够），跑 20 张真实图。
2. 引入**误差热力图 + 缩略图测试**，看主观念辨度是否够。
3. 加入 **S1 全局最优子集 + S4 描边 + S2 分区配额**，对比三组结果。
4. 接一个 VLM 做**裁判**（只评判、不生成），量化"AI 裁判的建议是否真的改善了结果"。
5. 把 `pictile-core` 包成 Web Worker，做**单页滑杆原型**，验证实时感。
6. 最后才做 PDF 导出、多板、库存模式。

第 4 步是整个项目的关键实验：**如果 AI 裁判的建议不能稳定改善结果，那"AI 辅助"这个故事就不成立，产品应该退回纯工具。** 这个验证应该在两周内做完，而不是在写完前端之后。

## 9. 本文的三条主张（如果只记三件事）

1. **AI 不进数值路径。** 转换是约束优化，AI 是感知器和评委。用生成模型做转换，等于放弃可复现、可局部修正、可解释。
2. **产品的护城河是色表数据 + 判断力，不是算法。** 300 行 numpy 谁都能写；实测色表和"这张图能不能拼"的判断才是壁垒。
3. **把调节轴从抽象参数换成时间、金钱和看得见的误差。** 用户不需要懂色彩学，只需要看到"改这个能省 40 分钟"。
